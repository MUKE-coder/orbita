# Grit Knowledge — for the agent building Grit Cloud / Orbita

> **Who wrote this:** the Grit framework maintainer. This folder is the authoritative
> description of **what a Grit app is and how it is built, configured, migrated, and
> deployed.** Orbita's "Grit-awareness" layer (Phase 2 of `project-phases.md`) must be
> built against *these facts*, not against assumptions.

**Read this folder after `prompt.md` and before you start Phase 2.** It is small and
dense on purpose — every file is deployment-relevant ground truth.

---

## The single most important thing

**A Grit app already ships everything needed to build and run it in production.** Every
`grit new` project comes with:

- **`grit.json`** — a machine-readable marker at the repo root that declares the
  architecture mode and which apps exist. *This is how you detect and classify a Grit repo.*
- **Production Dockerfiles** — one per service, tailored to the mode (single-binary with an
  embedded SPA, or a Go API + Next.js apps built from a pnpm monorepo).
- **`docker-compose.prod.yml`** — the production service topology (api, web, admin, postgres,
  redis, minio) using `expose:` only (nothing binds the host — a reverse proxy fronts it).
- **`.env` contract** — a known, fixed set of environment variables.
- **A migration path** — `grit migrate` (or the API's built-in migrator) applies schema.
- **Health, observability, and security endpoints** — all mounted on the Go API.

➡️ **Therefore Orbita should REUSE the app's shipped Docker files, not generate its own.**
Read `grit.json`, use the Dockerfiles that are already there, and only fall back to
generating when a file is genuinely missing. (This is the confirmed direction — see
`04-build-and-deploy.md`.) Where Phase 2.3 says "generate a multi-stage Dockerfile," read it
as "produce the correct build recipe" — and the correct recipe for a Grit app is *the one
Grit already committed to the repo.*

## Reference / test app — use this for Phase 2

There is a **real, pre-generated Grit app to test and inspect against**:

```
D:\LEARNING\Grit Framework\stoka          # generated by:  grit new stoka --full
```

`stoka` is a **`triple`** app (`grit.json.architecture = "triple"`, `frontend = "next"`) with
**every deployable shape present** — `apps/api`, `apps/web`, `apps/admin`, `apps/docs` — plus
`apps/expo` and `apps/desktop`, which are **not VPS-deployed** and must be ignored. It ships
the real `docker-compose.prod.yml`, `apps/{api,web,admin}/Dockerfile`, and
`apps/api/cmd/migrate/main.go`. Use it to:

- verify your Grit **detection** (read its `grit.json`, classify it `triple`, list services
  `api/web/admin/docs`, skip `expo`/`desktop`);
- verify your **build recipe** reuses its shipped Dockerfiles with the correct contexts (04);
- verify **addon env injection**, **migrations** (`cmd/migrate`), and **routing** against a
  real repo;
- serve as the sample app in the Phase 2 end-to-end test.

> If that exact path isn't available on the machine you run on, generate an equivalent with
> `grit new sample --full` (needs the Grit CLI + Go 1.24 + pnpm) — it produces the identical
> shape. Everything in this folder was written against real generated apps like `stoka`.

## How to keep this accurate

Grit is a live framework (current line: **v3.5x**). If a fact here ever conflicts with a
real generated app, the **generated app wins** — regenerate a reference app with
`grit new sample --full` and inspect it, or ping the Grit maintainer. Version-specific
numbers (ports, image tags) are called out where they matter; the *shapes* are stable.

The fastest way to see everything in this folder concretely: run
`grit new sample --full` (needs the Grit CLI + Go) and read the files it emits —
`grit.json`, `docker-compose.prod.yml`, `apps/api/Dockerfile`, `apps/web/Dockerfile`,
`apps/admin/Dockerfile`, `.env.example`.
